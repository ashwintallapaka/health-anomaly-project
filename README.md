# Health Anomaly Detection

A real-time pipeline that simulates wearable vitals, streams them through MQTT and
Kafka, flags anomalies with a Spark rule engine, persists everything to MongoDB, and
visualizes it on a live dashboard — plus a scheduled batch layer that turns each day's
streamed readings into the historical dataset tomorrow's analysis runs against. Built
as a course project on Google Cloud (Dataproc for Spark, Compute Engine for brokers,
Cloud Storage for the historical archive).

```
REAL-TIME
wearable (simulated) → MQTT → Kafka → Spark Streaming → MongoDB → dashboard
                                                          │
                                              readings_history (7-day TTL)
                                                          │
                                                  nightly export
                                                          ↓
BATCH                         gs://health-anomaly-data/historical/date=YYYY-MM-DD/
                                                          ↓
                            cron 02:00 → ephemeral Dataproc cluster → Spark batch
                                        (thresholds + personal-baseline z-scores)
                                                          ↓
                              gs://health-anomaly-data/batch_output/YYYY-MM-DD/
                                                          ↓
                                                      dashboard
```

The loop is the point: readings that stream in today are retained, exported to Cloud
Storage overnight, and become part of the accumulated dataset the batch job computes
per-patient baselines from. The historical data is produced by the pipeline itself
rather than hand-made for testing.

## Getting started

**Prerequisites:** Python 3.11, a running MQTT broker (e.g., Mosquitto) and Kafka
broker reachable from wherever you run these scripts, a MongoDB Atlas cluster (or
any reachable MongoDB instance), and a GCP project with billing plus the
Dataproc/Compute/Storage APIs enabled.

Each component keeps its own `requirements.txt`:

```bash
pip install -r mqtt/requirements.txt
pip install -r kafka/requirements.txt
```

Create a `.env` file (not committed) with:

```
MONGO_URI=mongodb+srv://<user>:<password>@<cluster-host>/?retryWrites=true&w=majority
```

### MQTT

```bash
export MQTT_BROKER=localhost      # default
export MQTT_PORT=1883             # default
export MQTT_TOPIC=wearable/data   # default
export ANOMALY_RATE=0.05          # default; share of readings deliberately abnormal

python mqtt/subscriber.py   # run first, in its own terminal
python mqtt/publisher.py    # sends a simulated reading every 2s
```

Each simulated patient (`P001`, `P002`, `P003`) has its own resting baseline (heart
rate, temperature, SpO₂), so normal readings vary around a patient-specific value
instead of one fixed number for everyone — this is what gives the batch job's
personal-baseline z-score check something real to key off of. An abnormal reading
perturbs exactly one vital past its threshold at a time (heart rate, SpO₂, or
temperature), chosen at random, rather than tripping all three rules at once.

### MQTT → Kafka bridge

```bash
python kafka/mqtt_to_kafka_bridge.py
# subscribes to wearable/data, forwards every message unchanged to Kafka topic health-data
```

> `kafka/producer.py` and `kafka/consumer.py` are earlier standalone demos and are
> not part of this flow — see [Status](#status).

### Spark — the rules

`spark/detection_rules.py` has no dependencies beyond plain Python:

```python
from detection_rules import is_anomalous
is_anomalous(spo2=89, temp=39.2, heart_rate=150)  # -> True
```

| Rule | Threshold |
|---|---|
| SpO₂ floor | `spo2 < 92` |
| Fever | `temp > 38.0`°C |
| Heart rate band | `heart_rate < 50` or `> 120` bpm |

```bash
pip install pyspark==3.5.3
python spark/test_detection_rules.py
```

### Spark — the streaming job

Reads the `health-data` Kafka topic, scores every reading, and writes three things to
MongoDB: an upserted `latest_vitals` document per patient (what the dashboard shows),
an idempotent `alerts` record whenever a rule fires, and every reading to
`readings_history` — which is what the batch layer later consumes.

```bash
pip install pyspark==3.5.3 pymongo python-dotenv

spark-submit --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.3 --py-files spark/detection_rules.py spark/streaming_job.py
```

`--py-files` is required: Spark workers are separate processes and won't find
`detection_rules` on the driver's path without it.

`readings_history` has a **TTL index expiring documents after 7 days** — MongoDB is
the hot operational store, Cloud Storage is the permanent archive. Create it once:

```bash
python3 -c "import os; from pymongo import MongoClient; from dotenv import load_dotenv; load_dotenv(); MongoClient(os.environ['MONGO_URI'])['health_anomaly'].readings_history.create_index('ingested_at', expireAfterSeconds=604800)"
```

To keep the streaming job alive across crashes and reboots, run it as a systemd
service — see [Running as systemd services](#running-as-systemd-services) below.

### Exporting history to Cloud Storage

```bash
python export_history_to_gcs.py              # defaults to yesterday
python export_history_to_gcs.py 2026-09-16   # or an explicit date
# -> gs://health-anomaly-data/historical/date=2026-09-16/readings.csv
```

### Spark — the batch job

Reads the accumulated archive and checks each reading two ways: the same fixed
thresholds as `detection_rules.py`, and a personal-baseline z-score (each patient's
own mean and standard deviation, flagging `|z| > 3`). Writes a per-patient summary —
reading count, avg/min/max heart rate, avg/max temp, avg/min SpO₂, and separate
threshold-anomaly and baseline-anomaly counts.

```bash
python spark/batch_processing.py
# defaults to data/historical_vitals.csv -> ./batch_output

python spark/batch_processing.py <input_path> <output_path>
```

Reading every date partition at once (what the scheduled run does) means baselines
get more accurate as the archive grows:

```
gs://health-anomaly-data/historical/date=*/readings.csv
```

### Scheduled batch runs

`infra/run_batch_job.sh` does the whole cycle: export yesterday's readings from
MongoDB to Cloud Storage, create a Dataproc cluster, submit the batch job across all
accumulated partitions, write results to a dated output folder, then delete the
cluster. Compute exists only for the duration of the run.

```bash
chmod +x infra/*.sh
./infra/run_batch_job.sh
tail -f /tmp/batch_run.log
```

Scheduled nightly via cron:

```
0 2 * * * /home/<user>/health-anomaly-project/infra/run_batch_job.sh
```

That completes the four batch-processing stages: **collection** (readings accumulate
in Cloud Storage), **scheduling** (cron at 02:00), **execution** (Spark on Dataproc
processes the full archive in one cycle), **output** (dated results in Cloud Storage).

Set a billing budget alert on your GCP project. An idle cluster is the fastest way to
burn credits, which is why the scheduled job destroys its own.

### Dashboard

`docs/index.html` reads `docs/data.json`, refreshing every 3 seconds. That file is
generated by `dashboard_export.py`, which polls MongoDB for current vitals and reads
the most recent Spark batch output from Cloud Storage:

```bash
python dashboard_export.py          # writes docs/data.json every 3s
cd docs && python -m http.server 8000
```

The page shows live patient vitals, the rule engine and which rules are firing, a
heart-rate vs. SpO₂ scatter, and the historical batch summary — all from real data,
none of it hardcoded.

> **The GitHub Pages deployment will render an empty dashboard.** `docs/data.json`
> is gitignored and only exists where `dashboard_export.py` runs, so the hosted page
> has nothing to fetch. Serve it from the machine running the exporter instead.

### Running as systemd services

Every long-running component now has a unit file in `infra/`, so the whole pipeline
survives crashes and reboots without anyone keeping a terminal open:

| Unit | Runs |
|---|---|
| `kafka.service` | The Kafka broker |
| `mqtt-kafka-bridge.service` | `kafka/mqtt_to_kafka_bridge.py` |
| `wearable-publisher.service` | `mqtt/publisher.py` |
| `spark-streaming.service` | `spark/streaming_job.py` |
| `dashboard-export.service` | `dashboard_export.py` |
| `dashboard-web.service` | `python -m http.server 8000` in `docs/` |

The shipped files hardcode the paths and usernames of the machines they were set up
on (`abhaykulkarni`, `chhayaahuja`) — edit `User`, `WorkingDirectory`, and the
`PATH`/`ExecStart` entries for your own environment before installing them.

```bash
sudo cp infra/*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now kafka mqtt-kafka-bridge wearable-publisher spark-streaming dashboard-export dashboard-web

sudo systemctl status spark-streaming        # swap in any unit name
journalctl -u spark-streaming -n 50 --no-pager
```

`mqtt-kafka-bridge.service` and `spark-streaming.service` both declare `After=`/
`Wants=` on `kafka.service` so they start in the right order; Mosquitto itself
isn't managed here and is assumed to already be running as its own service.

## Status

- **Done —** **The live pipeline is wired end-to-end**: `mqtt/publisher.py` → MQTT →
  `kafka/mqtt_to_kafka_bridge.py` → Kafka `health-data` → `spark/streaming_job.py` →
  MongoDB (`latest_vitals`, `alerts`, `readings_history`) → `dashboard_export.py` →
  `docs/index.html`.
- **Done —** **Batch processing runs on a schedule and consumes pipeline-produced data.**
  Cron triggers `infra/run_batch_job.sh` nightly; it exports MongoDB history to
  Cloud Storage, spins up a Dataproc cluster, runs `spark/batch_processing.py` over
  every accumulated date partition, writes a dated summary, and tears the cluster
  down. All four batch stages are covered.
- **Done —** **The dashboard renders live data.** Both the real-time view and the historical
  batch summary read from `docs/data.json`, regenerated every 3 seconds from MongoDB
  and the latest batch output. Nothing on the page is hardcoded.
- **Caveat —** **Baseline (z-score) anomaly counts previously read 0; the publisher has
  since been rewritten to address it.** The original `mqtt/publisher.py` sent every
  patient the same fixed "normal" reading and injected the same fixed "abnormal"
  reading ~20% of the time, so across a large accumulated dataset those abnormal
  values fell inside each patient's own standard deviation and stopped registering
  as statistical outliers — fixed-threshold detection still fired normally. The
  publisher now gives each simulated patient its own baseline vitals with natural
  variation around them, injects anomalies at a more realistic 5% (`ANOMALY_RATE`),
  and perturbs one vital at a time instead of tripping all three rules at once.
  Confirming this actually restores non-zero baseline-anomaly counts requires
  letting the archive accumulate under the new publisher and re-running the batch
  job — not yet verified against a fresh dataset as of this writing.
- **Caveat —** **The live streaming path still only knows fixed thresholds.** Mongo `alerts`
  documents are always `rule: "threshold"` — `streaming_job.py` hasn't picked up the
  personal-baseline z-score check that `batch_processing.py` does. Porting that logic
  across (reading baselines from the batch output) is the natural next step.
- **Caveat —** **Field and topic names still don't match `common/schemas.py`.** The live
  pipeline uses topic `wearable/data` → `health-data` and fields `user_id`,
  `heart_rate`, `body_temp_c`, `spo2` — consistent across the publisher, bridge, and
  streaming job. `common/schemas.py` describes a richer intended contract (topic
  `wearables/{user_id}/vitals`, Kafka topics `vitals.raw`/`vitals.clean`/`vitals.alerts`,
  fields like `systolic_bp`, `steps`, `lat`/`lon`, and an `ALERT_SCHEMA` with
  `metric`, `z_score`, `severity`). Treat it as target design, not current state.
- **Inactive —** **`kafka/producer.py` and `kafka/consumer.py` are not part of the live
  pipeline.** Earlier standalone demos using topic `health-data` but fields
  `patient_id`/`temperature`, which don't match the bridge or streaming job.
- **Cleanup —** **`data/historical_vitals.csv` is now a seed, not the batch input.** It was
  copied into the archive as the `date=2026-09-01` partition to bootstrap the
  dataset; the batch job reads every partition, most of which the pipeline produced.
- **Cleanup —** **`mqtt/screenshots/` is ~71 MB of raw PNGs and screen recordings** committed
  directly into git — most of the repo's weight. Consider a shared drive for future
  setup evidence, or at least compressing before committing.
- **Cleanup —** **`paho-mqtt` is declared in two `requirements.txt` files** with different pins:
  `mqtt/requirements.txt` has `paho-mqtt==2.1.0`, `kafka/requirements.txt` has it
  unpinned (needed because `mqtt_to_kafka_bridge.py` lives in `kafka/` but talks to
  both brokers). Worth pinning consistently.
